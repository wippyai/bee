# Build sequence

Status: the consolidated order of work from the six design rounds of
2026-09-08, in [thread records](THREAD_RECORDS.md),
[component layout](COMPONENT_LAYOUT.md), [registry extension](REGISTRY_EXTENSION.md),
[launch routing](LAUNCH_ROUTING.md) and
[placement and subscriptions](PLACEMENT_AND_SUBSCRIPTIONS.md). Each step names
what it touches, what it depends on and the proof that ends it. A step is
done when its proof passes on a populated store and after a restart, not when
its code exists. The cluster work proceeds in parallel; nothing below waits on
it, because owner epochs, resumable reads and uncertain outcomes are explicit
from step 2.

Current managed-agent checkpoint (September 14): four separately packaged harness
components have default window profiles, first-use resource setup and one public
managed route shared by the Agent picker and `bee claude|codex|agy|grok`. Claude,
Codex and Agy add Bee configuration to their admitted normal user configuration.
Grok snapshots the approved global TOML into private retained state, structurally
inserts only Bee MCP and keeps Bee hooks separate. The exact-source standalone
passes the four-provider selector plus real Grok authenticated and clean/restart
acceptance. Global Bee is still the Train A rollback point. Saved-profile editing,
durable four-provider session recovery, Docker and complete authenticated provider
turns remain open; the lower-level step proofs below do not imply those workflows
are complete. Source also supports a
host-selected instruction function with inherited actor/context and frozen
launch delivery; the picker does not yet edit that policy field. See
[Agent integration](handoffs/AGENT_INTEGRATION.md) and
[current global build](handoffs/GLOBAL_BUILD.md).

## Parallel lanes

- Steps 1 to 5 are one lane and touch only `bee.threads*` and `bee.approvals`.
- Step 6 runs alongside them on the workspace and storage side.
- Steps 7 and 8 can start once step 2 lands; they need no delivery to be tested against fixtures.
- Step 9 is the first point where the lanes meet, and the first adversarial consumer of everything before it.
- Step 11 uses native `exec.docker` and a digest-pinned image with the driver
  runtime in it. The optional `userspace/docker` component is not a release
  dependency.
- Step 14 is the first step that needs the cluster transport; everything before it works on one bee. The transport itself, supervisors, exposure and sessions are [the Hive protocol lane](HIVE_PROTOCOL.md), built in parallel.

## What is not in the sequence

Aider. Pause for batch mode. SIGSTOP. Bind-mounting host binaries. Per-driver executor entries. Any claim of Hive support before step 14's proof.
